# 第一部分　前端中控台（Tauri v2 + React）设计与架构方案

> **版本说明**：本文档为前端中控台的最新设计。目标不是简单监控看板，而是可替代本地终端的“前端控制台（Super Console）”。
> **2026-11-09 用户定稿**：采用 **Tauri v2 + React + Vite + TypeScript + Tailwind CSS + shadcn/ui**。Rust 端只负责用 Sidecar / Command 拉起现有 Python Daemon；**网络请求、SSE 监听、数据流全部在 React 的 JS/TS 侧实现**。先做隔离的“最小可运行脚手架”，测试通过并经用户确认后，才考虑并入项目。
> **方案 C 作废**：此前“原生 HTML + FastAPI 代理”的 C1 试验（`experiments/frontend-dashboard/`）仅作参考，不再投入，不迁入产品。

## 一、 设计定位与核心理念

1.  **一体化启动**：用户只启动桌面前端；前端通过 Tauri 的 Sidecar/Command 拉起现有 Python Daemon，并在 UI 显示“初始化 → 中控就绪”。
2.  **全要素可视化**：Agent 的角色、PID、PGID、状态（在线/离线/忙碌）、当前任务清晰可见。
3.  **前端即控制台**：不再要求 xterm 终端；用数据表格与 Console 列表流展示 Agent、任务、日志。所有信息流禁止聊天气泡。
4.  **强管控与熔断**：可对单个 Agent 执行停止；提供全局 `STOP ALL` 入口。

## 二、 核心 UI 模块规划

### 1. 顶部 Header
- Daemon 状态灯、监听地址、启动时间。
- 当前工作区路径与 Git Hash（后续接入）。
- 全局 `STOP ALL`。

### 2. 左侧栏：Agent 列表
- 表格/卡片：role、pid、pgid、status、alive、last_heartbeat、current_task_id、停止按钮。
- 点击选中 Agent，右侧/底部 Console 面板切换该 Agent 的日志（阶段二）。

### 3. 中间主区域：数据表格 / Console 列表流
- **不做 xterm.js 终端**；用主流可视化：数据表格 + 虚拟滚动日志列表。
- 任务列表：task_id、from_role、to_role、intent、status、updated_at。
- 日志/消息：按时间追加的 Console 行，等宽字体，不渲染聊天气泡。

### 4. 右侧栏：任务队列与审计
- 任务状态分组（queued/running/done/failed）。
- Daemon 日志与异常（可选）。

### 5. 底部：可折叠 Console 面板
- 默认折叠；展开后显示日志流/命令输出；支持拖拽改变高度。

### 6. 视觉与交互规范（2026-11-09 用户定稿）

**布局**：多面板 IDE 布局，面板支持拖拽改变宽高；底部 Console 可折叠。

**色彩**：深色模式为主。背景 `zinc-950`；卡片 `zinc-900`；边框 1px `zinc-800`；强调色使用低饱和度蓝/绿。

**组件**：shadcn/ui + Tailwind CSS。禁止任何聊天对话气泡；所有信息用 Console 列表流或数据表格展示。

**字体**：UI 用 Inter；代码、日志、终端用等宽字体（JetBrains Mono 或系统 monospace）。

**交互**：
- `Ctrl+K` 唤起全局命令面板。
- 日志列表强制虚拟滚动（Virtual Scroll）。
- 所有点击操作 100ms 内有视觉反馈；停止等操作采用乐观更新（先置 pending，失败回滚）。

## 三、 技术选型（2026-11-09 定稿）

| 项 | 选型 | 说明 |
|---|---|---|
| 桌面框架 | **Tauri v2** | 轻量；Rust 端只做进程托管 |
| 前端 | **React + Vite + TypeScript** | 所有网络/SSE/状态逻辑在 JS/TS |
| UI | **Tailwind CSS + shadcn/ui** | 深色 IDE 风格；组件按需复制 |
| 进程拉起 | Tauri **Sidecar 或 shell Command** | 拉起 Python Daemon；失败可见 |
| 网络 | **`@tauri-apps/plugin-http`** | 走 Rust 核心，绕过 WebView CORS；支持流式读取 |
| 文件读取 | **`@tauri-apps/plugin-fs`** | 读 `token` / `daemon.json`，token 不进前端包 |
| 实时通信 | **SSE**（`fetch` + `ReadableStream`） | 禁止 `EventSource` 与轮询 |
| 终端渲染 | **不需要 xterm.js** | 用表格/Console 列表流 |
| 虚拟滚动 | `@tanstack/react-virtual` | 日志与长列表 |
| 面板拖拽 | shadcn `resizable`（`react-resizable-panels`） | IDE 布局 |
| 测试 | Vitest + React Testing Library | 前端逻辑与 SSE 解析 |

**Rust 最小化原则**：Rust 端不加业务逻辑。网络请求、SSE 解析、终端数据流、命令面板全部用 JS/TS；若某段 Rust 逻辑复杂，优先使用 Tauri 官方插件或改在 JS 侧实现。

## 四、 联调清单

1.  **进程托管**：用 `@tauri-apps/plugin-shell` 的 `Command.create()` / `Command.sidecar()` 拉起 Daemon。需要声明 `shell:allow-spawn` / `shell:allow-kill`，并把允许的命令与参数写进 capability scope。若使用 Sidecar，二进制在 `tauri.conf.json > bundle > externalBin` 声明。
2.  **网络与 SSE**：用 `@tauri-apps/plugin-http` 的 `fetch()`（Rust 核心执行，绕过 WebView CORS）；SSE 通过 `response.body.getReader()` 按帧解析。**不要用浏览器原生 `EventSource`**（不能带 Authorization，且受 CORS 限制）。
3.  **Token**：从 `SENTINEL_ORCH_HOME/token` 读取（`plugin-fs`），只在 JS 内存中拼 Bearer 头；**不得写入 localStorage、不得打进前端包、不得打印日志**。
4.  **daemon 地址**：优先读取 `SENTINEL_ORCH_HOME/daemon.json` 的 `host` / `port`；脚手架可先用固定端口 `8765` 降低复杂度。
5.  **后端接口契约**：见 §5.2；前端只依赖这些接口，不为界面方便改 Daemon 语义。
6.  **CORS**：走 `plugin-http` 时不需要 Daemon 增加 CORS；若改用 WebView 原生 `fetch`，则必须处理 CORS。

### 5.2 后端接口契约（前端只依赖这些）

所有 Bearer 接口：`Authorization: Bearer <token>`。

| 接口 | 方法 | 用途 | 鉴权 | 说明 |
|---|---|---|---|---|
| `/health` | GET | 启动探测 | 无 | `{ok,pid,started_at}` |
| `/status` | GET | 一次性快照 | Bearer | `{daemon:{pid,host,port,started_at}, agents:[Agent]}` |
| `/events` | GET | 实时推送（SSE） | Bearer | `id:<revision>`；`event: snapshot\|heartbeat\|shutdown`；`data` 为 `/status` 形状；20s `: ping` |
| `/logs/stream?tail=&role=` | GET | 后端日志流（SSE） | Bearer | 回放 `logs/*.log` 最后 `tail` 行（默认 200、上限 1000）并跟随新增行；`event: log` + `data: {role,line,ts}`；不传 `role` 时推送全部并在约 2s 内纳入新角色日志；20s `: ping`；`9344d33` |
| `/logs/report` | POST | 外部会话日志上报 | Bearer | 入参 `{role,line}`；role 白名单、空白折叠、单行 ≤4000；追加到 `logs/<role>.log`，供 `/logs/stream` 跟随；`d481a93` |
| `/tasks?role=&status=` | GET | 任务列表 | Bearer | `{tasks:[Task]}` |
| `/discover` | POST | 重新探测 agent 存活 + 缓存整理 + 未注册进程 | Bearer | 无入参；恢复/清理缓存并扫描野生进程，返回 `{discovered, recovered, pruned, pending_registered, pending_pruned, agents, wild}`；`wild` 字段见下；`ffed730`、`4cb2cbc` |
| `/task` | POST | 任务详情 | Bearer | 入参 `{task_id}`，返回 `{task, messages}` |
| `/stop` | POST | 停止角色 | Bearer | 入参 `{role}` |
| `/observability` | GET | 汇总视图 | Bearer | MVP 可选 |
| `/shutdown` | POST | 停止 daemon | Bearer | 前端 MVP 不调用 |

字段契约（源码 `tools/orchestrator/registry.py`、`router.py` 为准）：
- Agent：`role, pid, pgid, job_id, status, started_at, last_heartbeat, command, updated_at, current_task_id, cost_tokens, cost_budget, alive, project`
- Task：`task_id, from_role, to_role, intent, pointer, acceptance[], status, idempotency_key, max_tokens, max_minutes, attempts, created_at, updated_at, ack_at, completed_at, artifacts[], cost_tokens`
- SSE：`id` = `revision`（单调递增）；`shutdown` 的 `data` 为 `{"stopping": true}`。

**已确认边界**：
- `/events` 的 snapshot/heartbeat 只含 daemon + agents，不含 tasks；前端收到 **snapshot** 后按需重取 `/tasks`（事件驱动失效重取）；**heartbeat 不触发** `/tasks` 重取。
- SSE 断开按指数退避重连；daemon 重启后 revision 归零，重连时重置去重游标。
- 日志流已提供 `GET /logs/stream`（`9344d33`）；stdin 转发仍无后端接口，不在本阶段。
- 项目隔离：daemon 由 home 推导 `project`（`SENTINEL_PROJECT_ROOT` 可覆盖）；注册 payload 携带不同 project 返回 409；`/status` 的 daemon 与 agent 均含 project（`4d1713f`）。
- MCP server 在带 `SENTINEL_ROLE` 时启动即注册，并每 15s 重注册（`SENTINEL_ORCH_HEARTBEAT_SECONDS` 可调），daemon 重启后可再识别；`POST /discover` 供前端手动重探存活（`4d1713f`）。
- 角色缓存：MCP 注册成功后按 `CLAUDE_CODE_SESSION_ID` 写 `<home>/agents/<session>.json`（session/role/ref/project/started_at/mcp_pid/claude_pid）；启动无 `SENTINEL_ROLE` 时回退缓存角色并继续心跳。daemon 每 30s（`SENTINEL_ORCH_AGENT_CACHE_SECONDS`）恢复存活缓存、删除死缓存；`/discover` 复用同一逻辑并返回 recovered/pruned（`7aa7a80`）。窗口重置后 session id 变化，需按唤醒流程重新注册一次。
- 未注册进程（P1，只读）：`/discover` 的 `wild` 为进程树根列表，字段 `pid/ppid/cwd/cmdline/create_time/source/root/child_pids/bound_role`；按 cwd 过滤到当前项目，排除 daemon/已注册/基础设施子树，`cmdline` 截断 300 字符并掩码密钥；2s 缓存（`4cb2cbc`）。前端「未注册进程」折叠区只展示，不提供绑定；P2 绑定未实现。
- 产品边界：`/stop` 仅对 `job_id` 非空的 daemon 托管 worker 生效；外部 Agent 返回 409 `external_agent`，UI 显示「外部进程」且无停止按钮；不杀 MCP server、不注入、无 UI 启动托管 worker 入口（`ffed730`）。

## 1. 背景与问题

当前「检测 Agent」只能识别两类来源：

1. MCP `orchestrator_register` 自报身份的 Claude Code 会话；
2. 这些会话写入 `.claude/orchestrator/agents/<session>.json` 的角色缓存。

这带来明确局限：

- 用户使用 **codex、pi 或手写 Python Agent** 时，中控台完全看不到它们；
- 没有任何注册协议的进程无法被现有逻辑发现；
- 「检测 Agent」实际上只做了「重新探测已登记 pid」，不是真正的发现。

目标是让 AgentSentinel 成为**异构 Agent 的中控平台**：既能识别自注册 Agent，也能发现项目内运行的野生活跃进程，并由用户手动绑定角色。

## 2. 目标与非目标

### 目标

- 基于 **进程 cwd + 进程树** 发现工作目录位于当前项目根目录内的活跃进程；
- 不依赖进程名（node/claude/python）匹配；
- 提供 `AgentDriver` 抽象：MCP 注册是一个 driver，未来 Codex 是另一个 driver；
- `/discover` 聚合返回已注册 Agent 与「未注册野生进程」；
- 用户在中控台手动把野生 PID 绑定为 `coder` / `tester` 等角色；
- 扫描只读取进程的 `pid/ppid/cwd/cmdline/create_time`，不读取环境变量、内存、文件或网络。

### 非目标

- 不自动把野生进程注册为 Agent（必须人工确认）；
- 不控制、不注入、不终止被发现的外部进程；
- 不替代 MCP 心跳/角色缓存；两者共存；
- 本轮不实现 CodexDriver 的具体逻辑，只预留接口。

## 3. 产品边界：中控只观察与调度，不终止外部进程

> 2026-11-10 用户拍板；与实现基线 `ffed730` 一致。本草案的嗅探、绑定只增加可观察性，不改变进程控制权。

- **停止范围**：`POST /stop` 仅对 `job_id` 非空的 daemon 托管 worker 生效；外部 Agent（MCP 会话、野生/手动绑定进程等 `job_id` 为空）返回 **409**，`reason="external_agent"`，不改状态、不杀进程（`tools/orchestrator/service.py:718-741`）。
- **前端呈现**：托管 worker 显示「停止」按钮；外部 Agent 操作列显示「外部进程」，不提供停止按钮（`experiments/frontend-dashboard-tauri/src/components/AgentTable.tsx:43,71-86`）。
- **禁止项**：不杀 MCP server、不注入进程、不新增「退出协议」；外部窗口由用户自行 Ctrl+C / 关闭。
- **UI 入口**：暂不提供 UI 启动托管 worker 的入口；托管 worker 仍由 daemon/CLI 创建。
- **与嗅探的关系**：发现、扫描、手动绑定只做观察与标注；绑定后仍不可停止（见 §11 安全边界、§8.2「不终止被绑定进程」）。

## 5. 总体架构

```
/discover
   │
   ├── ClaudeDriver        # 现有 MCP 注册/心跳/角色缓存
   ├── CwdProcessDriver    # psutil CWD + 进程树扫描（本草案新增）

```

### 5.1 AgentDriver 接口

```python
@dataclass(frozen=True)
class AgentCandidate:
    pid: int
    ppid: int
    cwd: str
    cmdline: str
    create_time: float
    source: str                 # "claude" / "cwd" / "codex"
    role: str = ""              # 已注册或已绑定的角色；野生候选为空
    registered: bool = False    # True = 已登记/已绑定；False = 野生候选
    root: bool = True           # 进程树根
    child_pids: tuple[int, ...] = ()


class AgentDriver(Protocol):
    name: str

    def discover(self, project: str) -> list[AgentCandidate]:
        """返回本 driver 能发现的 Agent 或候选；只读，不修改被扫描进程。"""
```

### 5.2 ClaudeDriver

- 包装现有 `_reconcile_agent_cache()` 与 registry 读取；
- `discover()` 返回已注册/缓存中可恢复的 Claude Agent（`registered=True`）；
- 现有 MCP 15s 心跳与缓存写入逻辑**保持不变**，仍属于注册侧；
- 本重构只把「发现/恢复」部分抽到 driver，避免 `/discover` 直接写死 Claude 逻辑。

### 5.3 CwdProcessDriver

- 使用 `psutil` 扫描全系统进程；
- 返回 `registered=False` 的野生候选；
- 默认只返回进程树根，子进程折叠为 `child_pids`；
- 不按进程名过滤。

### 5.4 CodexDriver（预留）

- 未来读取 Codex 的会话/进程/配置文件；

## 6. CWD + 进程树扫描算法

### 6.1 扫描步骤

1. `psutil.pids()` 获取全部 pid；
2. 对每个 pid 仅调用：
   - `Process(pid).cwd()`
   - `Process(pid).cmdline()`
   - `Process(pid).ppid()`
   - `Process(pid).create_time()`
3. 过滤：`cwd` 必须位于当前项目根目录下（`Path(cwd).resolve()` 前缀匹配，Windows 用 `normcase`）；
4. 构建项目内进程森林；
5. 排除基础设施；
6. 返回 root 候选。

### 6.2 进程树分组

- `root = cwd 在项目内 且（父进程不存在 或 父进程 cwd 不在项目内）`；
- 子进程不单独列为候选，记录到 root 的 `child_pids`；
- 若 root 的后代包含**已注册 pid**，视为已注册会话，不进入野生列表；
- 若一个野生进程有多个项目内子进程，只在 root 行展示子进程数量。

示例：

```
claude.exe (cwd=项目根, 子进程含 mcp_server.py 已注册 pid)
  └── python.exe mcp_server.py        ← 已注册，整棵树隐藏

bash.exe (cwd=C:\Users\...)
  └── python.exe my_agent.py (cwd=项目根)  ← 野生 root，展示
```

### 6.3 排除规则

以下进程及其子树不进入野生候选：

- daemon 自身 pid；
- 已注册的 MCP pid 及其子树；
- Console 自身（`agentsentinel-console.exe`）及 Vite/cargo 子树；
- `cmdline` 包含 `tools/orchestrator/service.py` 或 `tools/orchestrator/mcp_server.py` 的基础设施进程。

> 这是“基础设施排除”，不是“按进程名发现”。发现仍完全基于 cwd。

### 6.4 性能与缓存

- 全量扫描预计 100–500ms；
- 只由手动 `/discover` 触发，不进入 30s 缓存整理循环；
- driver 内缓存结果 2s，避免连续点击重复扫描；
- 单个进程 `AccessDenied`/`NoSuchProcess`/`ZombieProcess` 静默跳过。

## 7. 数据模型与持久化

`AgentRecord` / `agents` 表新增字段（SQLite migration，沿用现有 `_init` 模式）：

| 字段 | 说明 |
|---|---|
| `driver` | `claude` / `wild` / `codex`，默认空 |
| `pid_create_time` | 进程创建时间，防 PID 复用 |
| `cwd` | 绑定时的 cwd，仅展示/校验 |

绑定记录写入现有 registry，因此：

- daemon 重启后仍保留；
- 由 `process_alive(pid)` + `pid_create_time` 探活；
- 进程退出后标记 `stopped`，不自动删除。

- `agents`：已注册/已绑定，行为与现在一致；
- `wild`：新的未注册候选，只读展示；

- 旧前端忽略 `wild` 不会崩溃。

## 11. 安全边界

## 1. 组件与进程模型

```text
[编排服务 daemon] 127.0.0.1:<port> + SQLite
  ├── Registry：agents（role → pid/pgid/job_id/status/task）
  ├── Launcher：Popen + Windows Job Object
  ├── Router：tasks / messages / ack / completed
  ├── Monitor：心跳、超时、退出码、残留进程
  └── Ledger：任务步骤、幂等效果、成本（后置）

[agent 会话 doc] ── MCP(stdio) ──┐
[agent 会话 dev] ── MCP(stdio) ──┼──> 本地 HTTP 客户端 ──> daemon
[人工/调试]      ── CLI ────────┘
```

- **daemon**：唯一可以 `spawn` 角色的进程；持有 SQLite 与进程表。
- **MCP server**：每个 Claude 会话由 `.mcp.json` 拉起一个 stdio MCP 服务，代理到 daemon；doc 无 Bash，必须走 MCP。
- **CLI**：dev 与人工调试用；不替代 MCP。
- **worker**：模型 A 下即 `claude -p` 进程；启动时注入 `ROLE`、`ORCHESTRATOR_URL`、`TASK_ID`、`WORKSPACE_ROOT`、一次性 token。

## 2. 契约

### 2.1 SQLite（`.claude/orchestrator/registry.sqlite3`，WAL）

核心表见 §2.1，并补 `messages` 持久消息：

| 表 | 关键字段 |
|---|---|
| `agents` | `role PK`, `pid`, `pgid`, `job_id`, `status`, `current_task_id`, `started_at`, `last_heartbeat`, `command`, `updated_at` |
| `tasks` | `task_id PK`, `from_role`, `to_role`, `intent`, `pointer`, `acceptance`, `status`, `idempotency_key UNIQUE`, `max_tokens`, `max_minutes`, `attempts`, `created_at`, `ack_at`, `completed_at` |
| `messages` | `id PK`, `task_id`, `type`, `from_role`, `to_role`, `payload_json`, `created_at`, `delivered_at`, `read_at` |
| `steps` | `task_id`, `step_no`, `status`, `input_ref`, `output_ref`, `updated_at`（复合主键） |
| `effects` | `idem_key PK`, `task_id`, `action`, `target`, `output_ref`, `created_at` |

### 2.2 状态机

```text
agent: starting → idle → busy → terminated | failed
task:  queued → delivered → running → done | failed | timeout | budget_exceeded
```

- `delivered` 只表示服务已投递，不代表 agent 收到；收到显式 `ack` 才进入 `running`。
- 无 `ack` → `timeout`（120 秒），只重投 1 次；仍无 → `timeout` 并通知发起方/用户。
- 无 `completed` 不视为完成；以 `completed` + 产物路径为准。

### 2.3 消息（只发指针）

```json
{"type":"need","task_id":"T-...","from_role":"doc","to_role":"dev",
 "intent":"implement","pointer":"docs/local/交流区/.../P-12.md#s2",
 "acceptance":["测试通过","STATUS 已更新"],
 "budget":{"max_tokens":50000,"max_minutes":30},
 "idempotency_key":"T-...:dev:implement:v1"}

{"type":"ack","task_id":"T-...","role":"dev"}
{"type":"completed","task_id":"T-...","role":"dev","status":"done",
 "artifacts":["..."],"cost":{"tokens":0}}
{"type":"heartbeat","role":"dev","task_id":"T-..."}
```

### 2.4 幂等

- `idempotency_key` 唯一；重复 `need` 返回既有 `task_id`，不重复投递。
- 有副作用动作（写文件、提交）写 `effects`，执行前查重。
- 重试最多 2 次，退避 5s → 15s → 45s；不可逆动作不自动重试。

## 3. 进程隔离（Windows 11）

| 项 | 方案 |
|---|---|
| 启动 | `subprocess.Popen(..., creationflags=CREATE_NEW_PROCESS_GROUP)` |
| 进程组 | 记录 `pid` 作为 `pgid`（Windows 进程组 ID 等于组首进程 PID） |
| 容器 | `ctypes` 调 `kernel32`：`CreateJobObject` + `AssignProcessToJobObject` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` |
| 存活探测 | `OpenProcess` + `GetExitCodeProcess`；**禁止** `os.kill(pid, 0)` |
| 回收 | 先关 Job Object；失败再 `taskkill /PID <pid> /T /F` |
| 残留检测 | 任务结束检查 Job 内进程数；有残留 → `orphan_detected` 告警/回收 |
| 环境 | 子进程只拿必要变量：`ROLE`、`TASK_ID`、`ORCHESTRATOR_URL`、`ORCHESTRATOR_TOKEN`、`WORKSPACE_ROOT` |
| 日志 | stdout/stderr 重定向到 `.claude/orchestrator/logs/<role>-<task>.log` |
| 权限 | worker 的权限模式由用户决定；工具不得把 `ask` 降级或绕过 |

## 4. 通信与投递模型

### 4.1 模型 A：任务即进程（P0 验证，首期采用）

```text
A 发 need → 服务查 registry
  ├─ 目标角色有健康进程且 idle（模型 B 才成立）→ 投递
  └─ 否 → 启动全新进程（claude -p + 角色提示 + 任务契约）
        → worker 启动后调 MCP/CLI ack
        → 执行任务
        → 调 completed（含产物）
        → 退出；服务回收 Job Object
```

- 没有 idle 复用；一个任务一个新进程。
- 中途不能注入新消息；后续任务重新 `need`。
- 优点：进程隔离彻底、实现简单、无需常驻 stdin 协议。
- 代价：冷启动成本；会话上下文不跨任务保留（可后续用 `--resume` 或模型 B 解决）。

### 4.2 模型 B：常驻 worker（后续评估）

- 需要自建 worker 循环或 Claude Agent SDK；可能需要新依赖。
- 才能实现设计中的 idle/busy 复用与任务中途投递。
- 首期不做，除非 P0 证明 A 不可用且用户批准依赖。

### 4.3 MCP 工具面

| 工具 | 方向 | 说明 |
|---|---|---|
| `orchestrator.register` | agent → 服务 | 登记 role + pid/job（worker 启动时自动调用；也可人工） |
| `orchestrator.need` | agent → 服务 | 发起任务 |
| `orchestrator.ack` | agent → 服务 | 确认收到任务 |
| `orchestrator.completed` | agent → 服务 | 完成回执 + 产物 |
| `orchestrator.heartbeat` | agent → 服务 | 心跳 |
| `orchestrator.status` | agent/人工 | 查 agents/tasks/messages |
| `orchestrator.resolve` | agent | role → pid/status |

CLI 提供 `register/need/ack/completed/status/resolve`，供 dev 与调试；doc 只用 MCP。

## 10. 设计依据与 P0 证据（已合并）

> 本节由原 `docs/local/修订方案.md` 与 `docs/local/编排服务可行性验证.md` 合并而来（2026-11-08）。实现值与契约以本文 §1–§5 与 `使用与解析.md` 第一部分为准；旧设计中的初始值（如每任务 50k tokens）已被实现取代。

### 10.1 关键设计决策

背景：旧 v3 依赖 Claude 原生 `SendMessage` 跨会话唤醒，存在寻址依赖会话名、无法阻止后台偷跑、上下文隔离不彻底、缺少代码级 ACK 与进程组回收等问题。本编排服务替代的是“agent 之间直接通信”的链路，不替代 Claude 推理能力。

核心结论：

1. **进程隔离**：每个命名 agent 是独立 OS 进程，拥有独立进程组/生命周期；Windows 用 `CREATE_NEW_PROCESS_GROUP` + Job Object，POSIX 的 `start_new_session` 分支保留但非首期验收。
2. **中央编排服务**：注册中心、启动器、路由、监控、账本集中；agent 只与服务通信。
3. **注册表存进程句柄**：`role → {pid, pgid, status, current_task_id, ...}`，不存会话名/ref。
4. **只发指针 + 契约**：正文留在共享工作区，消息带路径、锚点、验收条件、预算与幂等键。
5. **只有编排服务能 spawn**：agent 只能发 `need`；任务结束检查进程组残留，有残留即告警/回收。
6. **显式确认**：无 ACK 不视为送达，无 `completed` 不视为完成；失败停下问用户，不猜、不轮询、不无限重试。

硬约束：

- 不允许 agent 自行调用 `Task`/`Agent` 或任何方式启动新 agent。
- 不允许通过 `setsid`、`nohup`、双 fork 等脱离进程组；检测到即视为违规。
- 不读项目外路径（如 `~/.claude`、用户主目录 transcript）。
- 每个 agent 只能写授权目录，其他目录只读。
- 所有跨 agent 消息必须经过编排服务。
- 任务必须有 `task_id`、幂等键、预算上限与验收条件。

# 第四部分　交互面板与开发日志设计（草案）

> 状态：**草案，待可行性评估与派单**（2026-11-11 收录）。末尾「请评估可行性」尚未执行；未改代码。

## 一、 背景与目标

当前的前端主要扮演“监控看板”角色，但在实际开发中发现两个痛点：
1. **原生终端体验极差**：直接用黑框跑 `claude`，推理过程（Thought）和工具调用会刷屏并覆盖用户的输入，导致交互极其混乱。
2. **历史上下文易丢失**：开发时间一长，终端滚过的信息就没了。我们需要一种机制，能清晰记录“用户提过什么要求”、“最终产出了什么结果”，方便后续排查是哪次改动引发了 Bug。

**目标**：将前端从“纯监控”升级为“可交互的工作台”，并建立轻量级的自动开发日志。

## 二、 核心功能模块

### 1. 富文本交互面板（类 Cursor Chat）
*   **UI 形态**：固定底部输入框（永不遮挡） + 上方消息流（按时间滚动）。
*   **数据解析与分离渲染**：
    *   中控（Daemon）拉起 `claude -p` 时，必须带上 `--output-format stream-json` 参数。
    *   前端需要解析这个 JSON 流，并根据 `type` 分类渲染：
        *   `thought` / `reasoning`：折叠进灰色面板（默认收起，点击展开）。
        *   `tool_use`：渲染为状态条（例如：`[⚙️ 正在读取 src/login.tsx]` 或 `[✅ 已修改代码]`）。
        *   `text` / `message`：使用 Markdown 渲染（支持代码高亮），作为最终结果展示。
*   **交互逻辑**：用户输入 -> 前端调用 Daemon 接口 -> Daemon 拉起/唤醒对应 Agent -> 返回 Stream 给前端渲染。

### 2. 自动开发日志（Dev Log）
*   **目的**：不需要复杂的版本控制，只需要一本清晰的“流水账”，记录“用户的 Prompt”和“Agent 的最终结果摘要”。
*   **记录方式**：
    *   每次一轮对话结束（Agent 吐完最终结果后），自动往项目内的 `docs/local/开发日志.md` 追加一条记录。
    *   **格式要求**：
        ```markdown
        ### [2026-11-11 15:30:00] 角色: dev
        **🗣️ 用户要求**: 把登录页的按钮改成蓝色。
        **📦 执行结果**: 已修改 `src/login.tsx`，新增 `className="bg-blue-500"`。
        **📄 变更文件**: src/login.tsx
        ```
*   **UI 辅助**：在前端侧边栏或底部 Console 增加一个“开发日志”Tab，实时展示这段 Markdown 渲染后的结果，方便随时回溯。

## 三、 后端改造需求（Daemon 侧）

为了实现上述功能，中控服务（Daemon）需要增加/改造以下接口：

1.  **双向通信接口**：
    *   需要一个 WebSocket 接口（如 `/ws/chat`）或 SSE + POST 组合。
    *   前端通过此通道发送用户的 Prompt。
2.  **进程 stdin 接管**：
    *   Daemon 收到前端 Prompt 后，通过 `subprocess.Popen` 启动 `claude -p --output-format stream-json`，并将 Prompt 写入其 stdin（或者作为启动参数）。
    *   实时读取 `stdout` 的每一行 JSON，原封不动地通过 WebSocket 推给前端。
3.  **日志落盘**：
    *   Daemon 在解析到流结束（如收到 `stop_reason` 或进程退出）时，提取用户的输入和最后一段文本输出，调用现有的文件写入工具，追加到 `docs/local/开发日志.md`。

## 四、 实施步骤建议

*   **Step 1**: 实现 Daemon 的 `POST /chat` 接口（暂用普通 HTTP 轮询或 SSE 返回流），测试底层能否成功调用 `claude -p` 并拿到 JSON 流。
*   **Step 2**: 前端实现 JSON 解析器，把 `thought` 折叠、`text` 渲染、`tool_use` 状态化，完成 UI 面板的静态展示。
*   **Step 3**: 打通双向交互：前端输入框 -> Daemon -> `claude` 进程。
*   **Step 4**: 在 Daemon 侧增加自动写入 `开发日志.md` 的逻辑，并在前端增加一个日志查看面板。
